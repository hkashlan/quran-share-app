# Design Document: Khatmah App

## Overview

The Khatmah App is a React Native + Expo mobile application backed by a self-hosted Supabase instance. It enables groups of users to collaboratively complete a full reading of the Quran by dividing the 30 Juz' among participants in a shared circle (Khatmah). The design covers authentication, Khatmah lifecycle management, Juz' assignment and progress tracking, gamification via Jazah rewards, an emergency fallback system, and real-time updates across all participants.

The architecture is a thin mobile client that calls Supabase directly (auth, database, real-time) with business logic split between client-side service modules and Supabase Row-Level Security (RLS) policies. No custom API server is required; Supabase Edge Functions are used only for scheduled tasks (cycle resets) and push notification dispatch.

---

## Architecture

```mermaid
graph TD
    subgraph Mobile Client (React Native + Expo)
        A[Expo Router Screens] --> B[Service Layer]
        B --> C[Supabase JS Client]
        B --> D[Notification Client]
    end

    subgraph Supabase (Self-hosted)
        C --> E[Auth]
        C --> F[PostgreSQL DB]
        C --> G[Realtime]
        H[Edge Functions] --> F
        H --> I[Push Gateway]
    end

    G -->|subscription| A
    I -->|FCM / APNs| D
```

### Key Architectural Decisions

- **Split Khatmah schema**: The `khatmahs` table holds only static configuration (name, lifecycle, assignment mode, etc.). Per-cycle, per-user data (assignments, completion, progress) lives in `khatmah_instances` — one row per Cycle. This keeps configuration stable across cycles while allowing cycle state to be created, reset, and queried independently. Real-time subscriptions target the active `khatmah_instance` row for a given Khatmah.
- **Client-side service modules**: `Auth_Service`, `Khatmah_Service`, `Assignment_Service`, `Progress_Service`, `Reward_Service`, `Invitation_Service` are TypeScript modules in `lib/` that wrap Supabase client calls. They are not network services — they are organizational boundaries.
- **Supabase Edge Functions for async work**: Scheduled cycle resets (monthly triggers) and push notification dispatch run as Edge Functions to avoid requiring the app to be open.
- **RLS as the authorization layer**: All data access rules (only Participants can read their Khatmah, only Creators can update config, etc.) are enforced via PostgreSQL RLS policies, not application code.

### RTL-Aware Component Wrappers (`components/ui/`)

The app supports Arabic (RTL) and English (LTR). Rather than scattering `I18nManager` or `writingDirection` checks throughout screens, all primitive React Native components are wrapped in thin Khatmah equivalents that automatically apply the correct layout direction based on the active locale from the i18n context.

```typescript
// components/ui/KView.tsx
// Wraps View — applies flexDirection mirroring and writingDirection for RTL
import { View, ViewProps } from 'react-native'
import { useLocale } from '@/hooks/useLocale'

export function KView({ style, ...props }: ViewProps) {
  const { isRTL } = useLocale()
  return <View style={[{ direction: isRTL ? 'rtl' : 'ltr' }, style]} {...props} />
}

// components/ui/KText.tsx
// Wraps Text — applies textAlign and writingDirection for RTL
import { Text, TextProps } from 'react-native'
import { useLocale } from '@/hooks/useLocale'

export function KText({ style, ...props }: TextProps) {
  const { isRTL } = useLocale()
  return <Text style={[{ textAlign: isRTL ? 'right' : 'left', writingDirection: isRTL ? 'rtl' : 'ltr' }, style]} {...props} />
}

// components/ui/KTextInput.tsx
// Wraps TextInput — applies textAlign for RTL
import { TextInput, TextInputProps } from 'react-native'
import { useLocale } from '@/hooks/useLocale'

export function KTextInput({ style, ...props }: TextInputProps) {
  const { isRTL } = useLocale()
  return <TextInput style={[{ textAlign: isRTL ? 'right' : 'left' }, style]} {...props} />
}

// components/ui/KScrollView.tsx — wraps ScrollView
// components/ui/KSafeAreaView.tsx — wraps SafeAreaView
// components/ui/index.ts — re-exports all wrappers
```

All screens and feature components use `KView`, `KText`, `KTextInput`, etc. instead of the bare React Native primitives. The `isRTL` value is derived from the user's profile `language` field, resolved at app startup and stored in the i18n context.

## Data Models

### `profiles` table

```sql
CREATE TABLE profiles (
  id            UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  display_name  TEXT,
  avatar_url    TEXT,
  language      TEXT NOT NULL DEFAULT 'ar',  -- 'ar' | 'en'; drives RTL and i18n locale
  jazah_total   INTEGER NOT NULL DEFAULT 0,  -- lifetime Jazah count; incremented on each award
  created_at    TIMESTAMPTZ DEFAULT now()
);
```

### `khatmahs` table (configuration only)

```sql
CREATE TABLE khatmahs (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name             TEXT NOT NULL,
  creator_id       UUID NOT NULL REFERENCES profiles(id),
  lifecycle_type   TEXT NOT NULL CHECK (lifecycle_type IN ('one_time', 'recurring')),
  reset_calendar   TEXT CHECK (reset_calendar IN ('gregorian', 'islamic')),
  auto_renewal     BOOLEAN NOT NULL DEFAULT false,
  assignment_mode  TEXT NOT NULL CHECK (assignment_mode IN ('manual', 'automatic')),
  jazah_multiplier INTEGER NOT NULL DEFAULT 1,
  invitation_uuid  UUID NOT NULL UNIQUE DEFAULT gen_random_uuid(),
  status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'completed')),
  created_at       TIMESTAMPTZ DEFAULT now()
);
```

> This table contains only static configuration. No per-cycle or per-user data lives here.

### `khatmah_instances` table (one row per Cycle)

```sql
CREATE TABLE khatmah_instances (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  khatmah_id   UUID NOT NULL REFERENCES khatmahs(id) ON DELETE CASCADE,
  cycle_number INTEGER NOT NULL DEFAULT 1,
  started_at   TIMESTAMPTZ DEFAULT now(),
  ended_at     TIMESTAMPTZ,
  status       TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'completed')),

  -- 30 Juz' user assignment fields (juz_1_user_id … juz_30_user_id)
  -- Each slot also stores the user's full name at assignment time (denormalized for join-free reads;
  -- name is frozen intentionally — historical accuracy is preserved even if the user later changes their display name)
  juz_1_user_id         UUID REFERENCES profiles(id),
  juz_1_user_full_name  TEXT,
  juz_2_user_id         UUID REFERENCES profiles(id),
  juz_2_user_full_name  TEXT,
  -- ... (juz_3 through juz_29 follow the same pattern)
  juz_30_user_id        UUID REFERENCES profiles(id),
  juz_30_user_full_name TEXT,

  -- 30 Juz' completion-status fields (juz_1_completed … juz_30_completed)
  juz_1_completed  BOOLEAN NOT NULL DEFAULT false,
  -- ... (juz_2 through juz_30 follow the same pattern)
  juz_30_completed BOOLEAN NOT NULL DEFAULT false,

  -- 30 Juz' plan-b user fields (juz_1_planb_user_id … juz_30_planb_user_id)
  -- Each slot also stores the plan-b user's full name at adoption time (same denormalization rationale as primary assignments)
  juz_1_planb_user_id         UUID REFERENCES profiles(id),
  juz_1_planb_user_full_name  TEXT,
  -- ... (juz_2 through juz_30 follow the same pattern)
  juz_30_planb_user_id        UUID REFERENCES profiles(id),
  juz_30_planb_user_full_name TEXT,

  -- 30 Juz' help-requested status fields (juz_1_help_requested … juz_30_help_requested)
  juz_1_help_requested  BOOLEAN NOT NULL DEFAULT false,
  -- ... (juz_2 through juz_30 follow the same pattern)
  juz_30_help_requested BOOLEAN NOT NULL DEFAULT false,

  -- 30 Juz' current-page fields (juz_1_current_page … juz_30_current_page)
  juz_1_current_page  INTEGER NOT NULL DEFAULT 0,
  -- ... (juz_2 through juz_30 follow the same pattern)
  juz_30_current_page INTEGER NOT NULL DEFAULT 0,

  UNIQUE (khatmah_id, cycle_number)
);
```

> The migration file will expand all 30 columns explicitly. The abbreviated notation above is for readability.
> When a Cycle resets, a new `khatmah_instances` row is inserted (with `cycle_number` incremented) rather than mutating the previous row, preserving historical cycle data.

### `khatmah_participants` table

```sql
CREATE TABLE khatmah_participants (
  khatmah_id UUID NOT NULL REFERENCES khatmahs(id) ON DELETE CASCADE,
  user_id    UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  joined_at  TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (khatmah_id, user_id)
);
```

### Jazah storage

Jazah totals are stored directly on the `profiles` row as `jazah_total`. There is no separate `jazah_records` table. When a Juz' is completed, `Reward_Service.awardJazah` issues a single `UPDATE profiles SET jazah_total = jazah_total + <multiplier> WHERE id = <userId>`. This keeps the Dashboard read path to a single row fetch with no joins and eliminates the need for an aggregation query.

```typescript
// Generated by: npx supabase gen types typescript --local > types/supabase.ts
// Re-run whenever the database schema changes.
// Import database row types from here throughout the codebase.

export type SupportedLocale = 'ar' | 'en'

// Configuration-only — maps to the `khatmahs` table
export interface Khatmah {
  id: string
  name: string
  creatorId: string
  lifecycleType: LifecycleType
  resetCalendar: ResetCalendar | null
  autoRenewal: boolean
  assignmentMode: AssignmentMode
  jazahMultiplier: number
  invitationUuid: string
  status: KhatmahStatus
  createdAt: string
}

// Per-cycle data — maps to the `khatmah_instances` table
export interface KhatmahInstance {
  id: string
  khatmahId: string
  cycleNumber: number
  startedAt: string
  endedAt: string | null
  status: InstanceStatus
  // juz fields indexed 1-30
  juzAssignments: Record<number, string | null>         // juz# -> userId
  juzUserFullNames: Record<number, string | null>       // juz# -> display_name at assignment time
  juzCompleted: Record<number, boolean>                 // juz# -> completed
  juzPlanbUsers: Record<number, string | null>          // juz# -> userId
  juzPlanbUserFullNames: Record<number, string | null>  // juz# -> display_name at adoption time
  juzHelpRequested: Record<number, boolean>             // juz# -> helpRequested
  juzCurrentPage: Record<number, number>                // juz# -> current page (0 = not started)
}

export interface UserProfile {
  id: string
  displayName: string | null
  avatarUrl: string | null
  language: SupportedLocale
  jazahTotal: number  // lifetime Jazah count; read from profiles.jazah_total
}
```

### Juz' page ranges

Each Juz' spans a fixed page range in the standard Mushaf (20 pages per Juz', pages 1–604). The `Progress_Service` validates submitted page numbers against these ranges.

```typescript

  1:  { start: 1,   end: 21  },
  2:  { start: 22,  end: 41  },
  // ... through 30
  30: { start: 582, end: 604 },
}
```

```typescript
export const RTL_LANGUAGES = new Set(['ar'])

export function isRTLLanguage(lang: string): boolean {
  return RTL_LANGUAGES.has(lang)
```

### Language Initialization

On app startup, after the user session is loaded, the active locale is set from `profile.language`:

```typescript
// app/(app)/_layout.tsx (simplified)
import i18n from '@/i18n'
import { isRTLLanguage } from '@/i18n/rtl'
import { I18nManager } from 'react-native'

async function applyLocale(language: string) {
  await i18n.changeLanguage(language)
  const rtl = isRTLLanguage(language)
  if (I18nManager.isRTL !== rtl) {
    I18nManager.forceRTL(rtl)
    // Expo requires a reload to apply RTL changes at the native level
  }
}
```

```typescript
import { useTranslation } from 'react-i18next'
import { isRTLLanguage } from '@/i18n/rtl'

export function useLocale() {
```

## Type Safety

### Supabase Generated Types

The `types/supabase.ts` file is generated from the live local Supabase schema and must never be edited manually. A dedicated script handles this:

```
scripts/
└── generate-types.sh   # Generates types/supabase.ts from the local Supabase instance
```

```bash
# scripts/generate-types.sh
#!/bin/bash
set -e

echo "Generating Supabase TypeScript types..."
npx supabase gen types typescript --local > types/supabase.ts
echo "Done — types/supabase.ts updated."
```

Register it as an npm script in `package.json`:

```json
{
  "scripts": {
    "generate-types": "bash scripts/generate-types.sh"

```


This produces a fully typed `Database` interface covering all tables, views, functions, and enums. All Supabase client calls use these types:

```typescript

  .from('khatmah_instances')

  .eq('status', 'active')
```

| Convention | Rule |

| Hook return types | All custom hooks have explicit return type annotations |

| Enums | Use `as const` objects + `keyof typeof` instead of TypeScript `enum` |

## Error Handling

| Scenario | Handling |
|---|---|
| Duplicate email on sign-up | Auth_Service surfaces Supabase `AuthApiError` with code `user_already_exists`; UI shows inline error |
| Invalid email format | Client-side validation before Supabase call; no network request made |
| Expired session | `onAuthStateChange` listener detects `SIGNED_OUT` event; app navigates to sign-in and clears AsyncStorage |
| Page number out of range | Progress_Service validates against `JUZ_PAGE_RANGES` before upsert; returns `ValidationError` |
| Duplicate Khatmah join | Invitation_Service checks `khatmah_participants` for existing row; returns `AlreadyMemberError` without insert |
| Automatic distribution with >30 participants | Assignment_Service caps primary assignments at 30; excess participants receive no `juz_X_user_id` assignment in the instance |
| Automatic distribution with <30 participants | Assignment_Service distributes multiple Juz' per participant using round-robin until all 30 `juz_X_user_id` fields in the instance are assigned |
| Real-time subscription failure | `useKhatmah` hook implements exponential backoff reconnect; stale data shown with a "reconnecting…" banner |
| Cycle reset on Islamic calendar | Edge Function uses `intl-hijri` or equivalent library; falls back to Gregorian if locale data unavailable and logs error |
| Network offline | Supabase JS client queues mutations; UI shows offline indicator via `NetInfo` |

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Jazah award equals multiplier

*For any* Juz' completion event in any Khatmah, the increment applied to `profiles.jazah_total` SHALL equal the Khatmah's `jazah_multiplier` at the time of completion.

**Validates: Requirements 4.1, 4.4**

---

### Property 2: Automatic distribution covers all 30 Juz'

*For any* Khatmah with at least 1 participant, after automatic distribution is triggered, every Juz' number from 1 to 30 SHALL have a non-null `juz_X_user_id` value.

**Validates: Requirements 5.4, 5.7**

---

### Property 3: Automatic distribution assigns at most one primary Juz' per participant when participants ≥ 30

*For any* Khatmah with 30 or more participants, after automatic distribution, no participant SHALL appear as the primary assignee (`juz_X_user_id`) for more than one Juz'.

**Validates: Requirements 5.6**

---

### Property 4: Page number validation rejects out-of-range values

*For any* submitted page number that falls outside the valid page range for the assigned Juz', the `Progress_Service` SHALL return a validation error and the stored `current_page` SHALL remain unchanged.

**Validates: Requirements 7.2, 7.4**

---

### Property 5: Invitation UUID maps to exactly one Khatmah

*For any* invitation UUID, resolving it SHALL return at most one Khatmah, and that Khatmah SHALL be the one for which the UUID was generated.

**Validates: Requirements 6.1, 6.2**

---

### Property 6: No duplicate Khatmah membership

*For any* user and any Khatmah, joining via the invitation URL SHALL result in exactly one row in `khatmah_participants` for that (khatmah_id, user_id) pair, regardless of how many times the join action is attempted.

**Validates: Requirements 6.6**

---

### Property 7: Jazah awarded to Plan-B User, not original assignee

*For any* Juz' that has been adopted by a Plan-B User, when that Juz' is marked complete, `profiles.jazah_total` for the Plan-B User SHALL be incremented and `profiles.jazah_total` for the original assignee SHALL NOT be incremented.

**Validates: Requirements 8.6**

---

### Property 8: Cycle reset clears all completion and progress state

*For any* Khatmah, after a cycle reset is executed, the newly created `khatmah_instances` row SHALL have all 30 `juz_X_completed` fields set to `false` and all 30 `juz_X_current_page` fields set to `0`.

**Validates: Requirements 9.1**

---

### Property 9: Auto-renewal preserves assignments across cycles

*For any* Khatmah with auto-renewal enabled, after a cycle reset, the new `khatmah_instances` row SHALL contain the same `juz_X_user_id` values that the previous instance held at the end of its cycle.

**Validates: Requirements 9.2, 3.7**

---

### Property 10: RTL wrapper applies correct direction for any language

*For any* language code, the RTL-aware component wrappers (`KView`, `KText`, `KTextInput`) SHALL apply `'rtl'` layout direction if and only if the language code is in the set of known RTL languages (e.g., `'ar'`), and `'ltr'` for all other language codes.

**Validates: RTL-aware component wrapper design**

---

### Property 11: i18n lookup returns non-empty string for all keys in all supported locales

*For any* translation key that exists in the English translation file, calling `t(key)` with any supported locale (`'ar'`, `'en'`) SHALL return a non-empty, non-undefined string.

**Validates: Multi-language support design**

## Testing Strategy

### Unit Tests (Jest + React Native Testing Library)

Focus on specific examples, edge cases, and pure logic:

- `Assignment_Service.distributeAutomatic` — verify round-robin distribution for participant counts of 1, 15, 30, and 31
- `Progress_Service.updatePage` — verify validation accepts boundary pages and rejects out-of-range values for each Juz'
- `Reward_Service.awardJazah` — verify `profiles.jazah_total` increments by the multiplier value for multipliers 1, 2, 3, 10
- `Invitation_Service.joinKhatmah` — verify idempotency (second call does not insert duplicate row)
- Cycle reset logic — verify new `khatmah_instances` row has all completion flags false and all current_page fields at 0
- `KText` / `KView` / `KTextInput` — verify RTL styles applied for `'ar'`, LTR styles for `'en'`
- i18n setup — verify `t('auth.signIn')` returns correct string for both `'ar'` and `'en'` locales

### Property-Based Tests (fast-check)

The feature involves pure business logic functions (distribution algorithms, validation, reward calculation, assignment invariants, RTL direction logic, i18n key coverage) that are well-suited to property-based testing.

Library: **fast-check** (TypeScript-native, works in Jest)

Each property test runs a minimum of **100 iterations**.

Tag format: `Feature: khatmah-app, Property {N}: {property_text}`

| Property | Test description |
|---|---|
| Property 1 | Generate random multipliers (1–100) and completion events; assert `profiles.jazah_total` increments by the multiplier value |
| Property 2 | Generate participant lists (1–100 users); assert all 30 Juz' assigned after distribution |
| Property 3 | Generate participant lists (30–100 users); assert no user appears as primary assignee more than once |
| Property 4 | Generate random page numbers; assert out-of-range values are rejected and stored page unchanged |
| Property 5 | Generate random UUIDs; assert each resolves to at most one Khatmah |
| Property 6 | Generate repeated join attempts; assert `khatmah_participants` row count stays at 1 |
| Property 7 | Generate adoption + completion events; assert Plan-B User's `jazah_total` increments and original assignee's does not |
| Property 8 | Generate khatmah_instances with arbitrary completion/progress state; assert new instance after reset has all fields false/0 |
| Property 9 | Generate khatmah_instances with auto-renewal; assert new instance assignments match previous instance |
| Property 10 | Generate arbitrary language codes; assert `isRTLLanguage` returns true iff code is in RTL set |
| Property 11 | For each key in `en.json`, assert `t(key, { lng: locale })` returns non-empty string for all supported locales |
